**ADR-010. Brand kit contrast defect (light text_subtle on bg).** Found by `packages/brand/contrast.test.ts` on 2026-11-09: in light mode, `text_subtle` #6D7571 on `bg` #F7F7F5 computes to 4.42:1, marginally below WCAG AA 4.5:1, although BRAND §4 states every text pair passes AA. **ADR-012. SheetJS `xlsx` 0.18.5 parses import files, inside `packages/core`.** Context: F2 needs .xlsx/.xls/.csv parsing including merged cells and Excel serial dates; parsing a buffer is a pure transform, so it lives in core next to the row validation that consumes it (the web service and the eval harness share it). Decision: pin `xlsx@0.18.5` (the last npm-published SheetJS build) as a core dependency; file reading is buffer-in/grid-out, no fs in core. **ADR-013. Egyptian mobile detection falls back to the numbering plan.** Context: the F2 golden fixtures caught that the bundled libphonenumber-js metadata returns an undefined number type for many valid EG numbers, so `whatsappCapable` was false for EVERY phone and new debtors were marked unreachable. Decision: trust the library type when present; when undefined, classify by the Egyptian numbering plan (mobile NSN = 10 digits starting 10/11/12/15). A regression test covers all four mobile prefixes plus a landline. Status: accepted (M1).

**ADR-014. Import duplicates attach invoices, never a second debtor.** Context: F2 dedupe marks rows whose normalized phone matches an existing debtor (or an earlier row in the same file). Decision: on commit, a duplicate row does not create a debtor; its invoice is created against the existing/first debtor. Rationale: in a receivables ledger a repeat phone almost always means another invoice for the same person, and silently dropping the invoice would lose money owed. Consequences: preview shows duplicates distinctly so the merchant can delete the file and fix it instead; flagged in RUNBOOK for human confirmation. Status: accepted (M1), pending human confirmation of the behaviour.

**ADR-015. WhatsApp Cloud API facts verified before coding F3 (AGENTS.md rule 6).** Checked 2026-11-09 against Meta's WhatsApp Business Platform documentation (developers.facebook.com/documentation/business-messaging/whatsapp) and its current secondary summaries of the same pages. Sending: `POST https://graph.facebook.com/{WHATSAPP_API_VERSION}/{WHATSAPP_PHONE_NUMBER_ID}/messages` with `Authorization: Bearer <token>`; template body `{messaging_product:"whatsapp", to:<digits, no leading +>, type:"template", template:{name, language:{code}, components:[{type:"body", parameters:[{type:"text", text}]}]}}`; response `messages[0].id` is the wamid stored for status correlation. Free-form text (`type:"text"`) is only valid inside the 24-hour customer-service window — outside it Meta returns 131047. Webhooks: GET handshake echoes `hub.challenge` as plain text when `hub.mode=subscribe` and `hub.verify_token` matches; POSTs carry `X-Hub-Signature-256: sha256=<HMAC-SHA256 of the RAW body, keyed with the app secret>` — verify BEFORE parsing; delivery is at-least-once, so dedupe by wamid is mandatory. Statuses arrive in `entry[].changes[].value.statuses[]` (`sent|delivered|read|failed`, failures carry `errors[].code`); inbound messages in `value.messages[]` (`from` = wa_id digits, `id`, `type`, `text.body`). Error-code mapping used by the sender: retry with backoff — 130429 (throughput), 131000/131016 (temporary); never retry — 131047 (re-engagement), 132000 (parameter count), 132001 (template missing/unapproved), 132015/132016 (template paused/disabled), 131031 (account restricted), 131030 (recipient not in allowed list); not-reachable (→ SMS fallback when enabled, mark debtor unreachable) — 131026 (message undeliverable / not on WhatsApp). Pricing: per-delivered-template-message since 2025-07-01, category decided by Meta, and service-window replies became billable 2026-10-01 (1,000 free/number/month) — therefore rates live in config/usage estimates, never constants in code. Status: accepted (M2).

**ADR-016. Reminder engine lives in `packages/reminders` (@tahseel/reminders).** Context: the planner/dispatcher/sender need DB access (not allowed in pure `packages/core`) and are used by both the worker (scheduled ticks) and the web app (re-plan on invoice/payment change, webhook processing). **ADR-011. One rate limiter for auth (ours), Better Auth's built-in disabled.** Found while exercising the running server (2026-11-09): sign-in attempts returned 429 after only 3 tries although the app limiter allows 10/min — debug logging proved the app limiter allowed 10/10 while Better Auth's own built-in limiter (production defaults) blocked from the 4th attempt with a non-uniform body. Decision: disable the library limiter (`rateLimit.enabled=false`) and keep the app's tested token-bucket limiter as the single source, so auth rate limiting follows the plan's uniform error shape. **ADR-017. Import undo vs reminders; reminders→invoices FK is ON DELETE CASCADE.** Context: M2's re-plan hook runs after an import commits, so imported invoices acquire scheduled reminder rows; M1's undo then violated the FK (found by the M1 integration suite after the M2 hooks landed). Decision: undo is blocked with `UNDO_BLOCKED_REMINDERS` (409) when any reminder for an imported invoice is `sent` or `queued` (real-world contact happened or is in flight); merely-planned reminders are deleted with their invoices. The FK `reminders.invoice_id → invoices.id` is ON DELETE CASCADE (migration 0004) so a planner insert racing the undo can never dangle or deadlock the delete — the planner only ever inserts `scheduled` rows, which is exactly the deletable class. Status: accepted (M2).

**ADR-018. Dispatcher semantics: grouping by dispatch day + payment sweep.** Two judgement calls inside F4, both pinned by acceptance tests. (1) Grouping: reminders are consolidated per debtor+channel by the day of the dispatch run, not by their original due day — a straggler step joins today's single message, which is what §6's "at most 1 message per debtor per day" means operationally; the template is taken from the most urgent step in the group and the amount variable is the group's total outstanding. (2) Sweep: each dispatcher cycle first cancels ALL future reminders of invoices that are paid/cancelled/written_off/disputed, even ones not yet due — so "paying cancels all future reminders within one dispatcher cycle" (§10 acceptance) holds literally, not only when the next step comes due. Skips performed by the sweep carry `invoice_paid` / `invoice_closed`. Status: accepted (M2).

**ADR-019. Paymob facts verified before coding F5 (AGENTS.md rule 6).** Checked 2026-11-09 against Paymob's official developer documentation (developers.paymob.com) as mirrored in Paymob's official AI Integration Skill repo (github.com/PaymobAccept/Paymob-AI-Integration-Skill, `universal-prompt.md`, crawled 2026-11-09) and its HMAC reference pages. **Intention API only** — the legacy 3-step flow (auth token → order → payment key) is deprecated and is NOT used. Create: `POST {PAYMOB_BASE_URL}/v1/intention/` (Egypt base `https://accept.paymob.com`) with header `Authorization: Token <secret_key>` (`sk_*`, server-side only; the public key `pk_*` is the only browser-safe key); body `{amount (integer, smallest unit — piasters), currency:"EGP", payment_methods:[<integration ids, integers>], items:[{name, amount, description, quantity}], billing_data:{first_name,last_name,email,phone_number,apartment,floor,street,building,shipping_method,postal_code,city,country,state} (ALL fields required, "NA" placeholders allowed, phone must be real), customer:{first_name,last_name,email}, special_reference:<our reference, echoed back as the order's merchant_order_id>, notification_url, redirection_url}`; response `{id, client_secret}`. Checkout: `{base}/unifiedcheckout/?publicKey=<pk>&clientSecret=<client_secret>`; the client_secret expires in **1 hour**, which is why payment links carry a 1-hour expiry. Webhooks: the transaction POST callback is the ONLY source of truth (the GET redirection params are unauthenticated and never fulfil anything); `hmac` arrives as a **query parameter**; verification is **HMAC-SHA512** (never SHA-256) over the concatenation (no separator) of these 20 `obj` fields in this exact order — `amount_cents, created_at, currency, error_occured, has_parent_transaction, id, integration_id, is_3d_secure, is_auth, is_capture, is_refunded, is_standalone_payment, is_voided, order.id, owner, pending, source_data.pan, source_data.sub_type, source_data.type, success` — with booleans rendered lowercase `true`/`false`, hex-lowercase digest, timing-safe compare. Dedupe on `obj.id` (the Paymob transaction id). An `is_auth:true` callback without capture means funds are HELD, not settled — never mark paid. Refund/void/capture: `POST {base}/api/acceptance/void_refund/refund` (resp. `/void`) and `POST {base}/api/acceptance/capture` with `Authorization: Token <secret_key>` and `{transaction_id, amount_cents}`. Transaction inquiry (reconciliation fallback) is the one flow that still uses the API key: `POST {base}/api/auth/tokens {api_key}` → short-lived token, then `GET {base}/api/acceptance/transactions/{id}?token=<token>`. Env consequences: new `PAYMOB_SECRET_KEY` + `PAYMOB_PUBLIC_KEY`; `PAYMOB_API_KEY` is kept for inquiry only; `PAYMOB_INTEGRATION_ID` holds the card integration id (test/live mode must match the keys or intention creation 404s). Status: accepted (M3).

**ADR-020. M3 data model: payment_links, statement_links, disputes; reversals are negative payments.** Context: §5 already defines `statement_links` (debtor_id, token_hash, expires_at, revoked_at, last_viewed_at) and `disputes` (invoice_id, raised_by, reason, status); F5 additionally needs somewhere to hold a Paymob intention before money moves, and an idempotency anchor for callbacks. Decision: (1) New tenant table `payment_links`: debtor, optional single invoice (null = debtor total), amount_minor snapshotted server-side at creation, `special_reference` unique (the correlation key the webhook resolves by, via the owner connection like the WhatsApp inbox), provider intention id, checkout URL, status `pending|paid|expired|failed|amount_mismatch`, `expires_at` (creation + 1h per ADR-019), `paid_payment_id`. (2) `payments` gains `gateway_transaction_id` (unique where set — the replay guard), `gateway_order_id`, and `reversal_of` (self-FK). (3) Refunds/chargebacks are reversing payments: a new confirmed row with **negative** `amount_minor` and negative allocations mirroring the original payment's allocations (capped at the original amounts), so the existing confirmed-allocations recompute reopens invoices with no special cases; the API boundary still rejects negative amounts from humans — negatives are only ever written by the reversal path. (4) Statement tokens: 32 random bytes, base64url in the URL, only the SHA-256 hash stored; lookup is by hash through the owner connection (the page is public and pre-tenant, exactly like a webhook), then all data reads/writes run inside `withTenant` for the link's tenant; unknown/expired/revoked tokens produce one identical generic not-found. (5) A debtor-raised dispute writes the `disputes` row AND moves the invoice to `disputed` through the existing status machine, so the M2 dispatcher sweep pauses its reminders with no new mechanism. Status: accepted (M3).

**ADR-021. Dispatcher claim order is debtor-contiguous.** Found during the M3 gate (2026-11-09): the load acceptance (50k reminders → 2,000 sends) failed with 75 reminders unsent. Root cause: the claim query ordered only by `due_at asc`, and with equal due times Postgres may return a debtor's rows split across two `limit` pages; the second part then hit the one-message-per-debtor-per-day rule in a later cycle and was rescheduled to tomorrow, so the run ended short. In M2 the heap happened to return insertion order, which masked it. Decision: claim order is `due_at asc, debtor_id asc, id asc`, keeping pages debtor-contiguous so grouping sees whole debtor sets. Residual: a single debtor with more due reminders than the page `limit` can still split — the daily-cap reschedule is then the correct behaviour. Status: accepted (M3).

**ADR-023. M5 pinned definitions: KPIs, forecast, cheque machine, plans.** (1) **Collection rate** = confirmed payments received in the calendar month ÷ (that amount + current total outstanding); 0 when the denominator is 0. **DSO** = (total outstanding ÷ invoiced in the last 90 days) × 90, rounded to 2 decimals; 0 when nothing was invoiced in the window. Aging buckets outstanding by days overdue: ≤0 current, 1–7 "0-7", 8–30, 31–60, >60 "60+". An invoice's "paid on" date (forecast + reminder performance) = the latest received_on among its confirmed allocated payments. (2) **Forecast**: lateness = paidOn − dueOn in days; median averages the two middle values (rounded); the 80th percentile is nearest-rank; debtor stats need ≥3 paid invoices, else tenant stats (≥3), else DEFAULT_LATENESS {median 7, p80 21} — the level used per invoice is reported in the explanation. Weeks are 7-day windows starting today; pre-today expected dates clamp into week 0; below 10 paid invoices tenant-wide the forecast is a not-enough-data state with zeroed weeks, never a fabricated line. The backtest trains only on invoices paid ≤ cutoff and predicts the ones actually paid in the next 8 weeks. (3) **Cheque machine**: held → deposited/returned/cancelled; deposited → cleared/bounced/returned; the rest terminal. Depositing a receivable creates a claimed payment; clearing confirms it through the M3 claim path; a bounce/return rejects a still-claimed payment or writes a core-planned reversing negative payment when the payment already confirmed; only bounces set the debtor risk flag. Payable cheques create no payments. Cheque photo extraction pre-fills the registration form (cheque-v1 prompt) — it never registers. (4) **Plans**: limits live in the `plans` config table (platform-level, no RLS, seeded by migration 0007 from core PLANS_SEED); quotas are usage_ledger whatsapp_utility+sms units per tenant-local month; warn at 80%, dispatcher skip_reason `quota_exceeded` at 100%. **All price_minor values are PLACEHOLDERS pending HUMAN_INPUTS #10** — they are labelled as such in code, UI and docs and must never be presented as decided. Subscription payment flows through the M3 PaymentProvider seam: with the fake provider the invoice is paid and the plan changes immediately; with a real provider a payment link is created, the invoice stays `issued`, and the plan changes only on confirmed payment. Status: accepted (M5).

**ADR-031. Financial leftovers batch (Prompt 02: H09, M01, M03, M04, M05, M06, M08, M09).** Context: the financial audit's remaining mediums/highs. Decisions: (1) **M03 — collected vs refunded (amends ADR-023):** `collectedInMonthMinor` is gross confirmed positive payments in the month; a new `refundedInMonthMinor` is the magnitude of confirmed negative payments in the month; `collectionRate` uses net (collected − refunded, floored at 0). Rationale: attributing a reversal to its original month would rewrite closed months retroactively; separate lines keep every month stable and make cross-month refunds visible. (2) **M09 — dispute resolution idempotency:** `disputes.resolution` (`reopen_invoice` | `cancel_invoice`, migration 0017) is stored on resolve; resolving an already-resolved dispute with the same resolution replays (no second audit row, no replan) and a different resolution is 409 DISPUTE_RESOLUTION_MISMATCH. The dispute and invoice rows are locked FOR UPDATE so concurrent resolutions serialize. (3) **M06 — receipt dedupe:** `files` gains UNIQUE(tenant_id, sha256) (migration 0017, dedupe-first DELETE; both FKs to files.id are ON DELETE SET NULL). `storeUpload` returns `deduped: true` for an existing hash (no second blob, no audit row) and a deduped upload forces the receipt outcome to `claimed`, never `auto_confirmed` — the duplicate-hash check fails by design. A sequential duplicate still creates a second CLAIMED payment for human review; only the double auto-confirm is closed. (4) **M01 — ledger reconciliation:** pure `reconcileLedger` (core) replays confirmed payments per (debtor, currency) in createdAt order — credit += amount − allocations — and checks (a) invoice paidMinor == Σ confirmed allocations, (b) a payment's allocations never exceed amount + credit held at that moment (reversals: |allocations| ≤ |amount|), (c) the replay ends at the stored credit for the debtor's credit currency and at zero otherwise. A non-zero remainder in a non-credit currency is `unattributed_remainder`: money received but represented in no balance. That case is REAL and reachable — a debtor holding EGP credit who overpays a USD invoice leaves a USD remainder that `recomputeDebtorCredit` never counts (it only sums the stored credit currency) — so the reconciliation surfaces it rather than fixing it; fixing it needs a multi-currency credit design decision (per-currency credit rows), deliberately not taken here. Surfaced as `payments.ledgerReconciliation` (tRPC) + a line on the debtor detail page next to the gateway reconciliation. (5) **M04 — forecast:** history trains on the amount actually collected (Σ confirmed allocations per invoice, new `loadCollectedByInvoice`), never the invoice's full amount; the forecast is single-currency (tenant default — the old code summed minor units across currencies); amounts past the 8-week horizon accumulate in `beyondHorizon` (rendered on the dashboard) instead of being dropped; every amount crossing into the number-based forecast passes a safe-integer assert (`assertSafeMinor` in core, `toSafeMinor` on the server — anything above 2^53 fails loudly, never silently truncated). `backtestForecast` keeps dropping out-of-horizon rows by definition (its horizon IS the evaluation window). (6) **M05 — reminder pre-send re-check:** `sendGroup` re-reads the group's invoices FOR UPDATE immediately before the provider call — same (dueOn, id) lock order as `lockDebtorInvoices`, so it serializes against `recordPayment` — cancels reminders for just-paid/closed invoices and re-quotes the live outstanding (a partial payment after claiming shrinks the message amount). Residual window, inherent to calling a provider outside a transaction: a payment that starts after this check commits, during the provider call itself. AGENTS.md rule 3 (never remind for a paid invoice) is otherwise enforced at the guard, sweep, and now send layers. (7) **H09 — disputed is frozen:** one rule everywhere — a disputed invoice contributes 0 to collectible outstanding and appears as a separate frozen subtotal (`outstandingFor`/`disputedFor` in core invoices.ts; list, detail, statement, KPI, pay-link and Copilot quote surfaces all use it). Settlement money CAN still be recorded against a disputed invoice; only auto-allocation skips it. (8) **M08 — Paymob parsing:** `amount_cents` accepts a safe-integer number or an all-digits string parsed via BigInt (exact above 2^53); the seven decision-critical booleans (success, pending, is_auth, is_capture, is_refunded, is_voided, error_occured) are REQUIRED — HMAC is verified on the raw object first, so strictness only rejects malformed payloads, never genuine callbacks. Status: implemented 2026-11-12/13; full suite green (see TESTING_EVIDENCE).
