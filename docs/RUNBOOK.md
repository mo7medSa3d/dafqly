## M6 checks (added 2026-11-09) — hardening, backups, rollback, pilot

### Backups (procedure — performed by the agent in this VM, NOT deployed in production)
- Backup: `DATABASE_URL=<prod url> ./scripts/backup.sh backups` → `backups/tahseel-<UTC timestamp>.dump` + `.sha256`. Timings measured here: dev DB (7 tenants) 117,075 bytes in ~1s; the 100k-invoice load DB: 18,644,196 bytes in ~6s.
- Restore drill (do this on staging monthly): create an empty DB, then `TARGET_DATABASE_URL=<staging url> ./scripts/restore.sh backups/<dump>` — the script verifies the sha256, restores with `--clean --if-exists`, and prints migration + row counts. Measured restore of the 100k dump: ~7s; counts matched the source exactly (tenants 1, debtors 5,000, invoices 100,000, payments 45,000, migrations 9).
- Production schedule (to deploy with hosting, HUMAN_INPUTS #13): daily `pg_dump` via cron at 03:00 Africa/Cairo, keep 30 daily dumps, copy off-host; retention/deletion of old dumps is an ops decision for the human.

### Rollback procedure
Migrations are FORWARD-ONLY (ADR-024). To roll back a bad deploy:
1. Stop the worker (kill switches below) if messaging is affected.
2. Redeploy the previous release tag (e.g. `git checkout v0.6.0-m5` artefacts/images).
3. If the bad deploy applied a migration, restore the pre-deploy backup into the production database (restore.sh above, target = production) — code rollback alone does NOT undo a migration.
4. Verify `/readyz`, sign in, dashboard totals, one dispatcher tick in the worker log.

### Incident basics (kill switches)
- Stop ALL sending now: set `GLOBAL_MESSAGING_PAUSED=true` (worker) or `DRY_RUN_MESSAGING=true` (renders, never sends) and restart the worker.
- Stop one tenant: tenant settings `sendingPaused` (also set automatically by the F3 quality guard — check `qualityPausedReason` + the audit row `tenant.sending_auto_paused`).
- Sends blocked unexpectedly: check the quota banner (F13: 100% of the monthly plan quota blocks with skip_reason `quota_exceeded`), trial expiry, and the M2/M3 RUNBOOK items (Meta/Paymob outages degrade to a growing queue — nothing is lost).
- Data rights: a tenant owner can export or permanently delete all tenant data from the dashboard danger zone (§8); deletion leaves only the platform tombstone (`tenant_deletions`).
